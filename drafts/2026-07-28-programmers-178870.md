## 문제

[프로그래머스 - 연속된 부분 수열의 합 (Lv.2)](https://school.programmers.co.kr/learn/courses/30/lessons/178870)

## 1. 문제가 준 조건 중에 하나는 안 쓰인다

제한사항에 이렇게 적혀 있다.

- `sequence`는 **비내림차순으로 정렬**되어 있습니다.
- 1 ≤ `sequence`의 원소 ≤ 1,000

정렬돼 있다는 말이 크게 보인다. 정렬이면 이분탐색이나 누적합 + 이진탐색이 먼저 떠오른다.

그런데 투 포인터로 풀고 나서 다시 보니 이상했다. **내 코드는 정렬을 한 번도 쓰지 않는다.** 크기를 비교하는 곳도, 순서를 가정하는 곳도 없다. 그냥 합이 작으면 오른쪽을 늘리고 크면 왼쪽을 당길 뿐이다.

의문: 그러면 이 풀이가 되는 근거는 뭔가? 정렬이 아니면 뭐가 이걸 떠받치고 있나?

## 2. 진짜 조건은 "원소가 모두 양수"다

투 포인터가 성립하려면 이게 보장돼야 한다.

- 오른쪽 끝을 늘리면 합이 **반드시** 커진다
- 왼쪽 끝을 당기면 합이 **반드시** 작아진다

이게 보장돼야 "합이 작으니 늘린다"는 판단이 항상 옳다. 만약 늘렸는데 합이 줄어들 수 있으면, 늘려야 할지 줄여야 할지 알 수가 없다.

그리고 이걸 보장하는 건 정렬이 아니라 **모든 원소가 1 이상**이라는 조건이다. 양수만 더해지니 늘리면 무조건 커진다. 정렬 여부는 아무 상관이 없다.

정말 그런지 직접 돌려봤다. 완전탐색 결과와 대조했다.

- 정렬 안 한 양수 배열 4,000건 -> 불일치 **0건**
- 음수와 0을 섞은 배열 4,000건 -> **1,445건 틀림**

정렬을 없애도 멀쩡하고, 양수 조건을 없애면 3분의 1이 깨진다. 이 풀이를 떠받치는 건 양수 조건이다.

문제가 정렬을 조건으로 준 건 아마 이분탐색으로도 풀 수 있게 열어둔 것 같다. 투 포인터 입장에서는 안 쓰는 조건이다.

## 3. 코드

```python
def solution(sequence, k):
    n = len(sequence)
    answer = [0,n-1,n]      # 👈 [시작, 끝, 길이] — 길이 초기값을 n으로
    left = 0
    right = 0
    length = 0

    sum_val = sequence[0]

    while left < n:
        if sum_val == k:
            length = right-left
            if length < answer[2]:   # 👈 < 이므로 같은 길이면 먼저 찾은 게 남음
                answer = [left,right,length]

        if right <n-1 and sum_val < k:
            right += 1               # 👈 작으면 늘린다
            sum_val += sequence[right]

        else:
            sum_val -= sequence[left]  # 👈 크거나 끝에 닿았으면 당긴다
            left += 1
    return answer[0:2]
```

길이 초기값을 n으로 둔 게 포인트다. 어떤 유효한 구간도 n보다 길 수 없으니 첫 정답이 무조건 갱신된다.

길이가 같을 때 앞쪽을 고르라는 조건은 따로 처리하지 않았다. 갱신 조건이 `<` 이고 구간을 왼쪽부터 훑으니, 같은 길이면 먼저 찾은 쪽이 그대로 남는다.

## 4. 포인터가 서로를 추월하는 순간

코드를 다시 보다가 걸린 부분이다. `left`와 `right`가 같은 자리에 있을 때 아래쪽 `else` 분기로 들어가면 어떻게 되나?

느리게 감아보자. `sequence = [1, 2, 3]`, `k = 100` 이라고 하자. (답이 없는 경우지만 흐름만 본다)

**[Step 1]** `left=0, right=0, sum=1`
합이 100보다 작고 `right`가 끝이 아니니 -> `right=1`, `sum=3`

**[Step 2]** `left=0, right=1, sum=3`
아직 작으니 -> `right=2`, `sum=6`

**[Step 3]** `left=0, right=2, sum=6`
작지만 `right`가 이미 끝(n-1)에 닿음 -> `else`로 감. `sum -= sequence[0]` 해서 `sum=5`, `left=1`

**[Step 4]** `left=1, right=2, sum=5`
또 `else` -> `sum -= sequence[1]` 해서 `sum=3`, `left=2`

**[Step 5]** `left=2, right=2, sum=3`
여기가 문제의 순간이다. 또 `else` -> `sum -= sequence[2]` 해서 `sum=0`, `left=3`
**이제 `left`가 `right`를 추월했고 구간이 텅 비어서 합이 0이 됐다.**

**[Step 6]** `left=3`, 즉 `left == n` -> `while` 조건이 깨져서 반복문 종료

즉 추월이 실제로 일어난다. 무작위 입력 3,000건을 돌려보니 **530건**에서 이 상태를 지나갔다.

처음엔 여기서 합이 음수까지 내려갈 거라고 생각했다. 계속 빼기만 하니까. 확인해보니 아니었다.

- 구간이 비어 합이 0이 되면, 0은 k보다 작으므로 **다음 루프에서 `right`를 늘리는 분기로 들어가 구간이 복구**된다
- `right`가 이미 끝에 닿아 복구가 불가능한 경우라면, `left`가 배열 길이에 도달해 **반복문이 그냥 끝난다**

그래서 합이 음수가 되는 경로는 존재하지 않는다. 3,000건 전부에서 음수는 안 나왔다.

결과는 맞지만 코드가 이걸 의도해서 허용한 건 아니다. 빈 구간을 지나간다는 사실이 코드만 봐서는 안 보인다. `left <= right` 조건을 명시하거나 주석을 달아두는 게 나중에 볼 때 낫겠다.

## 5. 요약 및 암기 키워드

- **투 포인터의 근거는 단조성**: 늘리면 커지고 당기면 작아지는 게 보장돼야 판단이 옳다. 이걸 만드는 건 보통 **양수 조건**이다.
- **문제 조건은 다 쓰이지 않는다**: 정렬 조건은 이 풀이에서 안 쓰였다. 조건이 보이면 "이게 내 풀이의 어디서 쓰이나"를 짚어보자. 안 쓰이면 다른 풀이를 열어둔 힌트다.
- **의심되면 돌려본다**: "정렬 없어도 되나?"는 4,000건 돌려서 0건으로 확인했다. 머리로 추론한 "음수까지 내려갈 것"은 3,000건 돌려서 틀린 걸 확인했다. 추론은 틀리고 실행은 안 틀린다.
