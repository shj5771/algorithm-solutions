# 알고리즘 풀이 → 네이버 블로그 초안

## 목표

백준허브가 자동 커밋한 풀이를 읽고, **네이버 스마트에디터에 붙여넣으면 바로 발행할 수 있는**
글 초안을 만든다. 사람이 하는 일은 붙여넣기와 발행 클릭뿐이어야 한다.

## 1. 대상 찾기

```bash
git -C . log --diff-filter=A --name-only --pretty=format:%H%x09%aI -20
cat drafts/.processed.json 2>/dev/null || echo '{"processed":[]}'
```

풀이 파일은 백준허브 규칙인 `<사이트>/<레벨>/<문제번호>. <문제명>/` 아래에 있다.
문제 키는 `<사이트>-<문제번호>` (예: `프로그래머스-42586`).

`.processed.json` 에 없는 키만 처리한다. 새 풀이가 없으면 **아무것도 만들지 말고**
"새 풀이 없음"이라고만 보고하고 끝낸다. 억지로 글감을 만들지 않는다.

한 번에 최대 3개까지만 만든다. 그 이상이면 오래된 것부터 3개를 하고, 남은 개수를 보고한다.

## 2. 재료 읽기

> ⚠️ **한글 경로는 리터럴로 쓰지 마라.** macOS는 파일명을 NFD로, git은 NFC로 저장한다.
> `cat "프로그래머스/2/178870. 연속된 부분 수열의 합/README.md"` 는 파일이 있어도 실패한다.
> 항상 문제 번호로 글로브를 잡아서 변수에 담아 쓴다:
>
> ```bash
> d=$(find . -type d -name "178870*" | head -1)
> cat "$d/README.md"; cat "$d"/*.py
> ```

각 문제마다:

- 풀이 코드 (해당 폴더의 소스 파일)
- 백준허브가 만든 `README.md` — 레벨, 소요시간, 메모리, 정확도가 들어있다
- **그 문제 폴더의 전체 커밋 히스토리** — 여기가 중요하다

```bash
git log --follow -p -- "<문제 폴더>"
```

같은 문제에 커밋이 여러 개면 **실패했던 시도가 히스토리에 남아 있다는 뜻**이다.
이게 글의 가장 값어치 있는 재료다. diff를 읽고 무엇이 어떻게 바뀌었는지 파악한다.

## 3. 글 쓰기

### 절대 규칙

1. **문제 지문을 복사하지 않는다.** 프로그래머스·백준 문제 지문은 저작권이 있다.
   링크를 걸고, 문제를 **자기 말로 2~3줄 요약**한다.
2. **없는 고생을 지어내지 않는다.** 커밋이 하나뿐이면 무엇에 막혔는지 알 수 없다.
   추측해서 쓰지 말고 그 섹션에 `<p>[여기는 직접 채워주세요 — 어디서 막혔는지]</p>` 마커를 남긴다.
   지어낸 서사는 이 블로그의 신뢰를 깎는 가장 빠른 길이다.
3. **코드에 실제로 있는 것만 설명한다.** 코드에 없는 최적화를 설명하지 않는다.

### 문체 — 이게 제일 중요하다

이 블로그 주인의 실제 글투를 따른다. **`~습니다` 체를 쓰지 마라.**

- 본문 서술은 **`~다` 체**: "감이 안 왔다", "결국 난 유형만 외웠던 것이다", "한번 더 정리한다"
- 단계·동작 설명은 **`~함` 명사형**: "0번 던전을 선택함.", "2층 방으로 진입 -> 1층의 for문은 일시정지"
- 화살표 `->` 를 자유롭게 쓴다
- **비유를 강하게 쓴다.** 추상적으로 설명하지 말고 그림이 그려지게 한다.
  실제 예: "각 층마다 복사본 컴퓨터가 돌고 있다", "1층 방 / 2층 방", "잠갔던 문을 열어주는 매너"
- 이모지는 **코드 주석 안에서 시선 유도용으로만** 쓴다 (`# 👈 재귀 호출`). 본문에는 남발하지 않는다
- 자기비판을 숨기지 않는다. 몰랐던 걸 몰랐다고 쓴다. 이 블로그의 힘은 여기서 나온다

### 구성

제목은 **`[유형]` 으로 시작**하는 형태도 쓴다: `[DFS] DFS/백트래킹에서 재귀와 for문의 흐름 이해하기`
문제 풀이 자체보다 **개념을 뚫은 지점**이 주제일 때 이 형태가 맞다.

본문 순서:

1. **`이 글을 적는 이유`** — 반드시 첫 섹션. 왜 이 글을 쓰는지, 뭘 몰랐는지, 뭘 느꼈는지.
   **이건 지어낼 수 없다.** 근거가 없으면 후보를 2~3개 제안하고 마커로 남긴다.
2. **`문제`** — 링크만. 지문을 요약해서 늘어놓지 않는다. 주인 글은 여기가 아주 짧다.
3. **`1. 가장 헷갈렸던 포인트`** — 번호를 붙이고, **제목에 내용을 담는다.**
   `남은 생각` 처럼 비어있는 제목을 쓰지 마라. `2. 각 층마다 복사본 컴퓨터가 돌고 있다` 처럼 쓴다.
   헷갈린 지점은 **`의문:` 으로 질문을 명시**하면 좋다.
4. **타임라인 추적** — 코드가 왜 그렇게 도는지는 `[Step 1]` ~ `[Step N]` 으로
   실행 순서를 아주 느리게 감아서 보여준다. 이 블로그의 대표 무기다.
5. **`요약 및 암기 키워드`** — 마지막 섹션. `키워드: 설명` 형태로 2~4개.
   나중에 다시 읽을 때 이것만 봐도 되게 만든다.

복잡도는 별도 섹션으로 크게 잡지 말고, 필요하면 한 줄로 흘린다.
주인 글은 **개념 이해**가 중심이고 코드 품질 평가가 중심이 아니다.
코드 리뷰처럼 "이렇게 고치면 낫다"로 흐르지 않게 주의한다.

분량은 코드 제외 800~2,000자. 타임라인 추적이 들어가면 자연히 길어진다.

## 3.5. 주장을 검증한다 — 건너뛰지 마라

글에 **코드 동작에 대한 주장**을 쓴다면 (복잡도 말고, "이 값이 음수가 된다", "이 조건은
없어도 된다", "정렬이 필요 없다" 같은 것) 반드시 실제로 돌려서 확인한다.

```bash
# 임시 파일은 스크래치패드에 만들고, 완전탐색과 대조한다
python3 - <<'PY'
# 풀이 함수 + 브루트포스 + 무작위 입력 수천 건 대조
# 주장하려는 상태(음수 도달, 포인터 추월 등)에 플래그를 심어 실제 발생 횟수를 센다
PY
```

**추론만으로 쓴 주장은 틀린다.** 실제로 이 레포의 첫 글에서 "합이 음수까지 내려간다"고
썼다가 3000건을 돌려 보니 0건이었다. 빈 구간(합 0)까지만 가고 바로 복구된다는 게 사실이었다.
검증하지 않았으면 틀린 분석이 블로그에 올라갔다.

검증한 숫자는 글에 그대로 쓴다. "정렬 없이도 4000건 중 불일치 0건, 음수를 섞으면 1445건 틀림"
같은 문장이 이 블로그를 다른 풀이 블로그와 구분 짓는 부분이다.

## 4. 출력 형식

**파일은 하나다. 평범한 마크다운이다.**

```
drafts/<YYYY-MM-DD>-<사이트영문>-<문제번호>.md
```

HTML을 직접 쓰지 마라. 예전에는 붙여넣기 서식을 살리려고 초안을 HTML로 만들었는데,
그러면 GitHub에서 열었을 때 태그만 보여서 **사람이 초안을 읽고 판단할 수 없다.**
검토 가능성이 붙여넣기 편의보다 우선한다.

변환은 `bin/md-to-naver.mjs` 가 한다. 마크다운 → 스마트에디터용 HTML → RTF.
그러니 초안은 읽기 좋은 마크다운으로만 쓰면 된다.

### 마크다운 작성 규칙

변환기가 다루는 문법만 쓴다.

| 쓸 것 | 변환 결과 |
|---|---|
| `## 제목` | `<h3>` |
| `#### 소제목` | `<h4>` |
| `**굵게**` | `<b>` |
| `` `코드` ``, `*기울임*` | `<i>` — 스마트에디터가 `<code>`를 안 받는다 |
| `[텍스트](url)` | `<a>` |
| `- 항목` / `1. 항목` | `<ul>` / `<ol>` |
| ` ```python ... ``` ` | `[코드블록 N]` 자리표시자 + 코드는 따로 추출 |

표와 이미지는 쓰지 않는다. 붙여넣을 때 깨진다.

### 제목 후보 섹션

첫 섹션은 반드시 `## 제목 후보` 로 시작하고 후보 3개를 번호 목록으로 넣는다.
변환기가 이 섹션을 **붙여넣기 결과에서 자동으로 제외**하므로, 검토용으로 남겨도 안전하다.

### 코드

코드는 본문 마크다운의 ` ```언어 ` 펜스 안에 그대로 넣는다. 별도 파일로 빼지 마라.
변환기가 본문에서는 `[코드블록 N]` 으로 바꾸고, `--code` 로 코드만 따로 뽑아준다.

## 5. 마무리

`drafts/.processed.json` 에 처리한 문제 키를 추가한다. 형식:

```json
{"processed": [{"key": "프로그래머스-42586", "draft": "drafts/2026-07-28-programmers-42586.html"}]}
```

그리고 사용자에게 보고한다:

- 만든 초안 파일 경로 (GitHub에서 바로 읽을 수 있는 마크다운이다)
- 각 글에서 **사람이 채워야 하는 마커가 있으면 그 위치**
- 복사 명령:
  - 본문: `bin/copy-draft.sh <경로>`
  - 코드: `bin/copy-draft.sh <경로> --code`

커밋은 하지 않는다. 사용자가 초안을 보고 판단한 뒤 직접 커밋한다.
단 스케줄 에이전트로 실행된 경우에는 커밋하고 푸시한다 — 그때는 사람이 그 자리에 없다.
