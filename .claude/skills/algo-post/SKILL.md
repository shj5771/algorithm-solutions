# 알고리즘 풀이 → 네이버 블로그 초안

## 목표

백준허브가 자동 커밋한 풀이를 읽고, **네이버 스마트에디터에 붙여넣으면 바로 발행할 수 있는**
글 초안을 만든다. 사람이 하는 일은 붙여넣기와 발행 클릭뿐이어야 한다.

## 1. 대상 찾기

```bash
git -C . log --diff-filter=A --name-only --pretty=format:%H%x09%aI -20
cat drafts/.processed.json 2>/dev/null || echo '{"processed":[]}'
```

풀이 파일은 백준허브 규칙인 `<사이트>/<레벨>/<문제번호>. <문제명>/` 아래에 있다.
문제 키는 `<사이트>-<문제번호>` (예: `프로그래머스-42586`).

`.processed.json` 에 없는 키만 처리한다. 새 풀이가 없으면 **아무것도 만들지 말고**
"새 풀이 없음"이라고만 보고하고 끝낸다. 억지로 글감을 만들지 않는다.

한 번에 최대 3개까지만 만든다. 그 이상이면 오래된 것부터 3개를 하고, 남은 개수를 보고한다.

## 2. 재료 읽기

각 문제마다:

- 풀이 코드 (해당 폴더의 소스 파일)
- 백준허브가 만든 `README.md` — 레벨, 소요시간, 메모리, 정확도가 들어있다
- **그 문제 폴더의 전체 커밋 히스토리** — 여기가 중요하다

```bash
git log --follow -p -- "<문제 폴더>"
```

같은 문제에 커밋이 여러 개면 **실패했던 시도가 히스토리에 남아 있다는 뜻**이다.
이게 글의 가장 값어치 있는 재료다. diff를 읽고 무엇이 어떻게 바뀌었는지 파악한다.

## 3. 글 쓰기

### 절대 규칙

1. **문제 지문을 복사하지 않는다.** 프로그래머스·백준 문제 지문은 저작권이 있다.
   링크를 걸고, 문제를 **자기 말로 2~3줄 요약**한다.
2. **없는 고생을 지어내지 않는다.** 커밋이 하나뿐이면 무엇에 막혔는지 알 수 없다.
   추측해서 쓰지 말고 그 섹션에 `<p>[여기는 직접 채워주세요 — 어디서 막혔는지]</p>` 마커를 남긴다.
   지어낸 서사는 이 블로그의 신뢰를 깎는 가장 빠른 길이다.
3. **코드에 실제로 있는 것만 설명한다.** 코드에 없는 최적화를 설명하지 않는다.

### 구성

```
제목:  [프로그래머스] 기능개발 (Lv.2) — 큐를 쓴 이유
```

본문 순서:

1. **문제** — 링크 + 자기 말 요약 2~3줄
2. **어떻게 접근했나** — 문제의 어떤 성질이 이 자료구조/알고리즘을 가리켰는지.
   "큐를 썼습니다"가 아니라 "앞에서만 빠지고 뒤에서만 들어오니 큐"라고 쓴다.
3. **막혔던 지점** — 커밋 히스토리에 근거가 있을 때만. 없으면 마커.
4. **코드** — `[코드블록 1]` 자리표시자를 넣는다 (아래 출력 형식 참고)
5. **복잡도** — 시간/공간. 왜 그렇게 되는지 한 줄.
6. **남은 생각** — 다른 풀이법, 더 줄일 수 있는 부분. 할 말 없으면 생략한다.

### 문체

- 담백하게. "~습니다"체.
- 과장 금지. "놀랍게도", "충격적인" 같은 말을 쓰지 않는다.
- 이모지를 쓰지 않는다.
- 분량은 코드 제외 400~800자. 짧아서 아쉬운 게 길어서 지루한 것보다 낫다.

## 4. 출력 형식

문제당 파일 2개를 만든다.

### `drafts/<YYYY-MM-DD>-<사이트영문>-<문제번호>.html`

붙여넣기용 본문. **마크다운이 아니라 HTML이다** — 스마트에디터는 마크다운을 모른다.
`##` 을 쓰면 그 기호가 그대로 화면에 보인다.

쓸 수 있는 태그는 스마트에디터가 받는 것만:
`<h3> <h4> <p> <b> <i> <ul> <ol> <li> <a> <blockquote> <br>`

`<pre>`, `<code>`, `<table>`, `style` 속성은 쓰지 않는다. 붙여넣을 때 깨진다.

코드가 들어갈 자리에는 이렇게 표시만 남긴다:

```html
<p><b>[코드블록 1]</b></p>
```

첫 줄은 `<h3>` 제목이 아니라 **제목 후보 3개**를 주석으로 남긴다:

```html
<!-- 제목 후보
1) [프로그래머스] 기능개발 (Lv.2) — 큐를 쓴 이유
2) [프로그래머스] 기능개발 — 배포 순서를 큐로 세는 법
3) 프로그래머스 기능개발 풀이 (Python, Lv.2)
-->
```

### `drafts/<...>.code.md`

`[코드블록 N]` 순서대로 코드 스니펫. 각 스니펫 위에 언어와 용도를 한 줄로 적는다.
사람이 스마트에디터의 코드블록 컴포넌트에 하나씩 넣는다.

## 5. 마무리

`drafts/.processed.json` 에 처리한 문제 키를 추가한다. 형식:

```json
{"processed": [{"key": "프로그래머스-42586", "draft": "drafts/2026-07-28-programmers-42586.html"}]}
```

그리고 사용자에게 보고한다:

- 만든 초안 파일 경로
- 각 글에서 **사람이 채워야 하는 마커가 있으면 그 위치**
- 복사 명령: `bin/copy-draft.sh <경로>`

커밋은 하지 않는다. 사용자가 초안을 보고 판단한 뒤 직접 커밋한다.
단 스케줄 에이전트로 실행된 경우에는 커밋하고 푸시한다 — 그때는 사람이 그 자리에 없다.
